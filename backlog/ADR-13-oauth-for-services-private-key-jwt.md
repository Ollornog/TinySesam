# ADR-13 — OAuth for services: `client_credentials` + `private_key_jwt`, paired by a code

Amends [ADR-11](ADR-11-oauth-authorization-server-in-tinysesam.md) for its second client kind, the one ADR-11
left to [T-60](T-60-oauth-for-services-client-credentials-private-key-jwt.md): a service or daemon without a person.

## Context

Services reach applications behind TinySesam today with an API key (`tsk_…`): a static bearer string that is
copied once into the service and then crosses every hop that terminates TLS — proxy logs, debug dumps, backups of
the service's configuration. [T-32](T-32-api-key-pairing-negotiate-a-key-on-first-contact-o.md) (PO wish 2026-11-20)
asked for pairing instead of copy-paste, a key negotiated on first contact, mandatory expiry with optional renewal,
and rotation. Its draft (PR #242) answered with an own design, ADR-10 (never merged, the number stays unused on
`main`): an Ed25519 key pair held by the client and an RFC 9421 HTTP Message Signature on **every request**,
checked by an ASGI layer in TinySesam.

Meanwhile ADR-11 built an OAuth 2.1 authorization server with opaque, resource-bound access tokens that forward auth
checks on every request. The PO goal for the connection concept: "how we design and provide MCP / service / M2M
connections cleanly, without users having to build anything themselves".

## Options

1. **ADR-10 draft — RFC 9421 per request.** Strong binding of each request. But: every protected application (or
   the proxy) must verify signatures — forward auth sees only a sub-request, so the signature base (`@target-uri`,
   `content-digest`) would have to be rebuilt behind the proxy (normalisation is exactly where such schemes break);
   own replay store per request; one more dependency (`http-message-signatures`); no OAuth client library speaks it.
   RFC 9421 itself says it is "not sufficient" as an overall security story.
2. **API key with pairing** (copy-paste replaced by a code, still a bearer key). Simple, but the key still travels
   with every request and lies at the server as a hash of something a copy can replay.
3. **`client_credentials` with `private_key_jwt`** (RFC 6749 §4.4, RFC 7523, OIDC Core §9). The service holds a key
   pair; it signs a short-lived client assertion for each *token request* and gets a short-lived access token that
   forward auth already checks — the same path as for a person's tools (ADR-11). Standard in every OAuth client
   library (Spring Security, the Go `oauth2` package, Authlib, MSAL, Keycloak, Okta, Entra).
4. **mTLS-bound tokens** (RFC 8705). Strongest binding, but lives at the TLS terminator; behind a proxy TinySesam would
   trust a forwarded certificate header, and it needs a CA, issuing and revocation. Rejected (as in ADR-10).

## Decision

**Option 3**, registered by a pairing code. What T-32/ADR-10 had is taken over where it fits, the rest replaced:

| From the ADR-10 draft | Here |
|---|---|
| Pairing code `XXXX-XXXX-XXXX-XXXX` (80 bits, no look-alikes), single use, 10 min, only a digest stored, rate-limited, audited | **taken over** (`oauth_pairing_minutes`, `magic_token` purpose `oauth_pairing`; goes with the account's other open links on lock and password reset) |
| Key pair generated by the client, only the public key at the server | **taken over** — Ed25519 or P-256, stored as a public JWK; a JWK with a private member is refused |
| Proof of possession at pairing (request signed with the new key) | **taken over** as a JWS with `typ` `tinysesam-pairing+jwt`, `aud` = issuer, `nonce` = SHA-256 of the code |
| Reference client `tinysesam.client` with CLI | **taken over and rebuilt**: `tinysesam-client pair/token/request/rotate/info`, key file 0600, token cache, `httpx`/`requests` auth classes |
| RFC 9421 signature on every request, ASGI layer, nonce store per request | **replaced** by `private_key_jwt` at the token endpoint + a short-lived opaque token (one check path for people and services; no proxy normalisation; no own replay logic per request) |
| `rotate_on_login` (server marks, client rotates on its next request) | **replaced** by client-driven rotation: the key has a lifetime, the client rotates at half of it by itself. A service account has no login, and the owner's login cannot reach the client anyway |
| `renew_on_login` | **replaced** by the same rotation: every new key starts a new lifetime. Expiry stays mandatory (default 90 days) |
| Extra `[pairing]` = `http-message-signatures` | **replaced** by extra `[services]` = `joserfc` (only `cryptography` below it) |

### Rules, with their source

- **Client assertion** (RFC 7523 §3; RFC 10070 = draft-ietf-oauth-rfc7523bis, Nov 2026): `iss` = `sub` = client ID;
  **`aud` is the issuer identifier as the sole value** (a string or a one-element list), compared as a plain
  string — the token endpoint URL is refused (RFC 10070 forbids it for client authentication: audience injection,
  2025). `exp` required, at most 300 s ahead (30 s clock skew); `iat`/`nbf` not in the future; `jti` required and
  single use until `exp` (`oauth_assertion`, written only after the signature verified — a stranger cannot fill it).
  `typ`: `client-authentication+jwt`, or `JWT`, or none (RFC 10070: servers should not refuse untyped JWTs); any
  other type — e.g. TinySesam's own gate token — is refused.
- **Algorithms**: `Ed25519` (RFC 9864, fully specified), `ES256`, and `EdDSA` for an Ed25519 key (deprecated by RFC
  9864, still what many libraries send). The header's `alg` must be on the list **and** belong to the stored key's
  type; joserfc verifies with exactly that algorithm. No `none`, no HMAC (a public key as an HMAC secret fails
  before any verification), no RSA (not needed; smaller surface). The key is found by the client ID (and `kid`),
  never taken from the token: `jwk`, `jku`, `x5u`, `x5c` are not consulted; `crit` with anything unknown is refused.
- **No own cryptography**: joserfc ≥ 1.7.6 (the floor without a known advisory, OSV 2026-11-20) verifies and signs;
  TinySesam parses the compact header only to choose the key. The gate token (ADR-9) keeps its own small signer — it
  only signs, the proxy verifies.
- **Errors**: every refused assertion answers `invalid_client` (401) with a generic description; the reason goes to
  the audit log (`oauth_client_auth_failed`, throttled per address and reason).
- **Tokens**: the opaque access tokens of ADR-11 (`tsat_`, HMAC digest with the pepper), lifetime
  `oauth_service_token_ttl_sec` (default 900 s, at most an hour), **no refresh token** (the service asks again —
  RFC 6749 §4.4.3), scope `mcp` only. One grant per (service, resource) carries them, so forward auth, revocation
  and audience binding are ADR-11's code.
- **Resource** (RFC 8707): a service is paired for named resources from `oauth_resources`; `resource` outside them →
  `invalid_target`; without `resource` only when exactly one is allowed.
- **Account and roles**: the service acts as the account it was paired for — a service account (admin panel) or a
  person's own account (account page, fresh session). Forward auth reads the account, the service row and the roles
  on every request; a locked account or a revoked service is refused at the next request. The admin flag is never
  set (as an automation key, R6-5); an optional role scope is trimmed to the account's roles and intersected again
  per request.
- **Who may pair**: from an interactive session only — never an API key, an access token or an app password; the own
  account from a freshly confirmed session (`_require_fresh`, B-12); any account from the admin panel (also fresh,
  owner protection).
- **Key rotation**: `POST /auth/oauth/service/keys`, authenticated with an assertion of **the** current key (the one
  without `retire_at`); the new public key comes with a proof of possession (`typ` `tinysesam-key+jwt`, `sub` = client
  ID). It becomes current at once; every other key stays valid for one hour (`KEY_OVERLAP_SEC`: tokens and assertions
  in flight, other processes that share the key file), then it is refused and deleted by `gc()`. The overlap counts
  at the token endpoint only — a key within its overlap may not rotate (amended 2026-11-21 after attack round A,
  A-2: with a copied old key a stranger rotated in a key of their own, and the rightful new key ran out after the
  hour instead). At most three keys at once. The same new key sent again is a success (lost answer), also with an
  assertion of the key it replaced, since the proof shows possession of the now current key. The client writes the
  new key to its file as *pending* before the server learns it, so a crash in between loses nothing: on restart it
  sends the pending key again with the old key's assertion and gets the success answer.
- **Revocation**: one service (account page, panel, `revoke_service_client`) or all of an account — on lock, admin
  password reset, password reset and "end all sessions", the same path as API keys and app passwords. Keys are
  deleted, tokens stop at once. Events `oauth_service_paired` (also mailed with `notify_new_access`) and
  `oauth_service_revoked`.
- **Switch**: `oauth_service_clients` (off by default; needs `oauth_enabled` and the extra). Off means: no grant type,
  no pairing route, and tokens a service still holds are refused.

### DPoP (RFC 9449) — not now

DPoP would bind each access token to the service's key, so a copied token is useless. But the check belongs at the
resource: every request through forward auth would need the `DPoP` proof, `htm`/`htu` rebuilt from the proxy's
forwarded headers (the normalisation problem of option 1 again) and a `jti` store per request. That is not "small
effort", and a 15-minute token bound to one resource already limits a copy. Left as
[T-68](T-68-dpop-for-service-tokens.md).

## Consequences

- One more optional dependency (`joserfc`, BSD-3-Clause, by the Authlib author; already pulled in by Authlib ≥ 1.6 for
  `[oidc]`/`[gateway]`). The core install does not change.
- Schema 21 (additive): `oauth_service_client`, `oauth_client_key`, `oauth_assertion`. A service is also an
  `oauth_client` row (no redirect URI) so that grants, tokens and forward auth are ADR-11's.
- A token request costs one signature verification and one insert (replay entry); forward auth stays a lookup.
- Copying the key file is copying the service — like any credential. Rotation limits how long a copy works (at most
  `KEY_OVERLAP_SEC` at the token endpoint, never for a further rotation); the device list (account page, panel) shows each service with its last token request, address and key expiry.
- Other languages need no TinySesam code: any OAuth client with `private_key_jwt` works once paired; the pairing
  request is one JSON POST (documented in the README).
- What this does not do: binding the access token to the client (DPoP, T-68), mTLS, service-to-service delegation
  (token exchange, RFC 8693).
